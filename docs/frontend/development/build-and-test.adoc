= Build and Test

This section describes the developer workflow for the Angular client. All commands run from `frontend/`. Prerequisites (Node 22, Docker, the development JWT signing key) and the backend stack itself are covered in `docs/consumer/development/build-and-test.adoc`; this section only repeats what is frontend-specific.

== npm script inventory

Every script in `frontend/package.json`:

[cols="1,3", options="header"]
|===
| Script | What it does

| `ng` | The Angular CLI directly, for one-off commands like `npm run ng -- generate ...`.
| `start` | `ng serve`: the Angular dev server on port 4200, proxying `/api` to the BFF (see below).
| `build` | `ng build`: a production build into `dist/frontend/browser`.
| `watch` | `ng build --watch --configuration development`: rebuilds on file change without serving.
| `test` | `ng test`: Vitest unit tests through the Angular CLI.
| `lint` | ESLint over `src/` (TypeScript and templates), honouring the suppressions baseline in `eslint-suppressions.json`.
| `lint:prune` | The same, removing baseline entries that no longer occur. Run it after migrating a file to the I18N or STORAGE adapter.
| `test:eslint-rules` | `node --test`: the tests of the local ESLint rules in `eslint-rules/`.
| `format` | Prettier, rewriting files under `src/` in place.
| `format:check` | Prettier in check-only mode; fails if any file would change.
| `i18n:check` | `node scripts/check-i18n.mjs`: fails on hardcoded user-facing text (see below).
| `generate:client` | Regenerates the TypeScript API client via the consumer Gradle build (see below).
| `generate:jwt-key` | Runs `consumer/scripts/generate-dev-jwt-key.sh` to create the dev JWT signing key.
| `e2e` | `playwright test`: runs the Playwright specs against an already-running stack.
| `e2e:ui` | `playwright test --ui`: the same specs in Playwright's interactive UI mode.
| `e2e:full-stack` | The full-stack journeys (`playwright.full-stack.config.ts`) against an already-running stack; nothing is mocked.
| `e2e:full-stack:ui` | The same journeys in Playwright's interactive UI mode.
| `e2e:docker:up:backend` | Generates the JWT key, then starts only the `bff` service (and its dependencies) from `docker-compose.e2e.yml`.
| `e2e:docker:up` | Backend up, regenerate the TypeScript client, then build and start the full stack including the frontend container.
| `e2e:docker:down` | `docker compose down -v`: removes containers and volumes for a clean next start.
| `e2e:docker:logs` | Follows the compose logs of the e2e stack.
| `e2e:docker:ps` | Lists the e2e stack's containers.
| `e2e:stack:run` | One shot: `e2e:docker:up`, then `e2e`, then `e2e:docker:down`.
|===

== Dev server

`npm start` runs `ng serve` on http://localhost:4200. The serve target in `angular.json` points at `proxy.conf.json`, which forwards every `/api` request to `http://localhost:8080`. The browser therefore talks only to the dev server, and the dev server relays API calls to the BFF. This mirrors the nginx setup used in Docker (see the xref:serving[Serving the Built App] section) and avoids cross-origin requests.

The proxy only forwards; it does not start anything. The backend stack must already be up, or every API call returns a connection error. Start it as described in `docs/consumer/development/build-and-test.adoc`, or use `npm run e2e:docker:up:backend` from `frontend/`, which also generates the JWT key first.

== Unit tests

Unit tests run on Vitest (a fast test runner from the Vite ecosystem) through the Angular CLI. The `test` target in `angular.json` uses the `@angular/build:unit-test` builder with `runner: vitest` and `vitest.config.ts`. That config file's only job is forcing the Ionic/Stencil packages through Vite's resolver.

[source,bash]
----
cd frontend
npm test
----

Specs are `.spec.ts` files colocated with their subjects under `frontend/src/app/`. They mainly cover the signal-backed feature stores (`savings.store.spec.ts`, `loans.store.spec.ts`, `transfers.store.spec.ts`, and so on), the HTTP interceptors (`error.interceptor.spec.ts`), and the form-heavy components (registration, login, transfer form, loan application, change password).

== End-to-end tests (Playwright)

Playwright (a browser automation framework) drives a real Chromium browser against the dockerized, nginx-served app. `playwright.config.ts` sets:

* `baseURL` `http://localhost:4443`, overridable with the `PLAYWRIGHT_BASE_URL` environment variable
* a single worker with `fullyParallel: false`, so specs run one at a time
* retries 2 and a 180-second per-test timeout in CI; 0 retries and 30 seconds locally
* trace, screenshot, and video captured only for failures
* one project: Desktop Chrome

The specs live in `frontend/playwright/tests/`:

[cols="1,3", options="header"]
|===
| Spec | Covers

| `registration.spec.ts` | The registration walk from identity form to OTP to success, asserting the OTP and document key never land in browser storage.
| `loans.spec.ts` | Guarded-route redirect, the payment button hidden on inactive loans, the repay OTP step-up happy path, and the wrong-OTP error snackbar.
| `transfers.spec.ts` | Guarded-route redirect, history-to-form navigation, the transfer OTP step-up happy path, and the wrong-OTP error snackbar.
| `savings.spec.ts` | Guarded-route redirect to `/login` when unauthenticated.
| `summary.spec.ts` | Guarded-route redirect to `/login` when unauthenticated.
|===

The specs stub every BFF response in the browser with Playwright's `page.route`, so they exercise the served app and its routing, forms, and interceptors without depending on backend data. They therefore do not require `consumer/scripts/seed-demo.sh`: seeding is for the interactive demo, described in `docs/consumer/development/demo.adoc`.

The stack comes from `docker-compose.e2e.yml` at the repository root. That compose file pulls in the whole backend stack via `include: consumer/compose.yaml` and adds one `frontend` service: the nginx image that serves the built app on host port 4443. The usual way to run everything is the one-shot script, which brings the stack up (including client regeneration), runs the specs, and tears down with `-v`:

[source,bash]
----
cd frontend
npm run e2e:stack:run
----

To iterate on specs, run `npm run e2e:docker:up` once and then `npm run e2e` (or `npm run e2e:ui`) repeatedly, tearing down with `npm run e2e:docker:down` when finished.

=== Full-stack journeys

The specs above check the app in isolation. The journeys in `frontend/playwright/full-stack/` check that it works with the real BFF, Fineract and email delivery. They run against the same stack with nothing mocked, configured by `playwright.full-stack.config.ts`, and `npm run e2e:stack:run` runs both suites.

Each test starts from nothing and builds its own consumer the way the product does:

. *Staff set-up in Fineract.* `support/fineract.ts` calls Fineract's REST API as the default `mifos` user (port 8888). It creates an active client with an SSN identifier, two USD savings accounts (one funded with 5,000), and a disbursed 10,000 loan, mirroring the Cucumber suite's `FineractSeeder`. If the tenant has no `SSN` document type under `Customer Identifier`, it adds one, because the registration form offers SSN and Aadhaar.
. *Self-registration in the app.* The test fills in the registration wizard and confirms it with the OTP emailed to the consumer.
. *Multi-factor sign-in.* The test signs in with the password and the emailed second factor.

Every OTP is read from Mailpit, the SMTP sink in the stack (port 8025), by `support/mailpit.ts`. The BFF keeps one pending OTP per user, so a test clears the consumer's inbox before each action that sends a code.

[cols="1,3"]
|===
|Spec |Journeys

|`auth.spec.ts`
|Register and sign in with the second factor, sign out, and be redirected from a protected page. A wrong password and a wrong code are refused. Reset a forgotten password with an emailed code and sign in with it.

|`accounts.spec.ts`
|The summary lists the accounts opened in Fineract; a savings account shows its balance and the deposit transaction; a loan shows its disbursal.

|`beneficiaries.spec.ts`
|Add, rename and delete a beneficiary, each change confirmed by OTP; adding one of your own accounts is refused.

|`transfers.spec.ts`
|Transfer between your own accounts, and pay a beneficiary within its limit. A payment above the limit is refused. Balances are checked in Fineract, not only on screen.

|`loans.spec.ts`
|Preview a schedule, submit an application and withdraw it (with the status checked in Fineract); repay a loan from savings with an OTP.

|`profile-settings.spec.ts`
|The profile shows the registered client; change the password with an OTP and sign in with the new one; no connected apps for a new consumer.

|`audit.spec.ts`
|The audit trail records the sign-in; another customer's account is refused; the side menu and the language switcher work.
|===

Tests are independent: each seeds its own client, so they can run in any order or alone. Two Ionic details matter when you write a new one, and `support/ionic.ts` handles both:

* An `<ion-button>` with `routerLink` renders as a link, so look it up with `action()` rather than `getByRole('button')`.
* Selects open in an overlay attached to `<body>`. Use `select()`.

To iterate, bring the stack up once with `npm run e2e:docker:up`, then run `npm run e2e:full-stack` (or `e2e:full-stack:ui`). The service URLs default to the compose ports; override them with `PLAYWRIGHT_BASE_URL`, `FINERACT_API_URL` and `MAILPIT_URL`. CI runs the journeys in their own workflow, `e2e-full-stack.yml`, which builds and starts the whole stack for each combination it tests:

[cols="1,1,1"]
|===
|When |Fineract |BFF

|Pull requests and pushes to `main`
|The image pinned in `consumer/compose.yaml`
|JVM jar

|Nightly
|Pinned, and `develop` (an early warning when upstream changes break the BFF)
|JVM jar, and the GraalVM native image (with the pinned Fineract)

|Manual dispatch
|Any `apache/fineract` tag
|Either
|===

Each run records the images under test in the job summary and keeps the HTML report. On failure it also keeps the traces, videos and container logs. The native variant layers `docker-compose.e2e.native.yml` onto the e2e stack; it builds the binary first, as `build-native.yml` does.

== Regenerating the TypeScript client

`npm run generate:client` changes into `consumer/` and runs the `generateTypescriptClient` Gradle task, which scrapes the OpenAPI spec from the running BFF and writes the typed Angular client to `frontend/src/openapi-client` (imported as `@bff/client`). Two rules carry over from the backend pipeline (full details in `docs/consumer/development/build-and-test.adoc`):

* The backend stack must be up, because the spec is read from the running application.
* Delete the old output first: the generator does not remove files for endpoints that no longer exist, so stale services linger otherwise. The directory is gitignored generated output.

[source,bash]
----
cd frontend
rm -rf src/openapi-client
npm run generate:client
----

== Lint, format, and i18n check

`npm run lint` runs ESLint over all TypeScript and templates under `src/`, with the suppressions baseline described in the adapter-boundary architecture page; `ng lint` does not read that baseline. `npm run format` and `npm run format:check` apply Prettier with the settings embedded in `package.json` (100-character lines, single quotes, the Angular parser for HTML). `npm run i18n:check` parses every component template under `src/app` and fails the build if it finds hardcoded user-facing text, meaning literal text nodes or attributes such as `title`, `placeholder`, and `aria-label`. All copy must therefore resolve through the translation pipe or be added to the script's allowlist. CI runs `lint` and `format:check` in the `prettier-eslint.yaml` workflow and `i18n:check` in the `i18n-check.yml` workflow (see the continuous-integration section of `docs/consumer/development/build-and-test.adoc`).

=== Static analysis rules

ESLint carries the frontend's SonarQube-equivalent checks. SonarQube's JavaScript and TypeScript rules reach ESLint as `eslint-plugin-sonarjs`, which is LGPL-3.0-only, an ASF Category X licence, so this project does not use it. Following apache/fineract-backoffice-ui, which removed it for that reason, the rules come from permissively licensed plugins instead, on top of `@eslint/js`, `typescript-eslint` and `angular-eslint`:

[cols="2,1,3", options="header"]
|===
| Plugin | Licence | What it covers

| `eslint-plugin-unicorn`, `unopinionated` set | MIT | Correctness rules: primitive wrappers, array misuse, regex and string pitfalls. The `recommended` set is not used because most of it is style.
| `eslint-plugin-security`, `recommended` set | Apache-2.0 | `eval`, unsafe regular expressions, non-literal file system paths, timing-unsafe comparison, pseudo-random numbers.
| `eslint-plugin-import-x` with `eslint-import-resolver-typescript` | MIT, ISC | Unresolved and duplicate imports. The backoffice uses `eslint-plugin-import`, which does not support ESLint 10; `import-x` is its maintained fork.
| `eslint-rules/cognitive-complexity.js` | Apache-2.0 | SonarQube's cognitive-complexity metric at its default threshold of 15, implemented in this repository (copied from the backoffice) because no maintained permissive package exists. `npm run test:eslint-rules` pins its scoring.
|===

Rules from these sets that report style rather than defects, or whose autofix does not compile against this project's ES2022 `lib`, are switched off in `eslint.config.js`, each with its reason next to it. Some SonarQube rules have no permissive equivalent and are not covered, among them `no-duplicate-string`, `no-identical-functions` and `no-duplicated-branches`. Publishing to SonarCloud itself would need a project and token provisioned by ASF Infra and is out of scope for now.
